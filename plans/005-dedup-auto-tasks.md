## Why this matters

When a warranty status transition happens, `generateAutoTasks` creates the
workflow tasks for the destination status (from the `warranty_task_templates`
table). It only guards against **one** duplication case — the
`AGUARDANDO_CLIENTE → EM_ANALISE` return loop. Every **other** re-entry into a
status regenerates the whole task set.

Concrete bug: an admin approves a claim (`EM_ANALISE → APROVADO`) → the APROVADO
tasks are created. Later they revert it (`revertStatus`, an admin override, back
to `EM_ANALISE`) and approve again → `generateAutoTasks` runs for `APROVADO` a
second time and creates a **duplicate set** of the same tasks. The task list and
the "Próximos Passos" checklist then show each task twice. This is a real
rework path (the revert/override feature exists specifically for corrections).

The fix makes task generation **idempotent per stage**: a stage's tasks are
created at most once per claim.

## Current state

`backend/src/warranty/warranty.service.ts` — `generateAutoTasks` (the dedup is
the first `if`):

```ts
private async generateAutoTasks(
  claimId: string,
  fromStatus: string,
  toStatus: WarrantyStatus,
  userId: string,
): Promise<void> {
  // Evitar duplicatas: retorno AGUARDANDO_CLIENTE → EM_ANALISE não gera tarefas
  if (fromStatus === 'AGUARDANDO_CLIENTE' && toStatus === 'EM_ANALISE') {
    return;
  }

  const templates = await this.prisma.warrantyTaskTemplate.findMany({
    where: { toStatus, active: true },
    orderBy: { sortOrder: 'asc' },
  });

  if (templates.length === 0) return;
  // ... resolves assignee names, then:
  const taskData = templates.map((tpl) => ({
    claimId,
    title: tpl.title,
    assignee: roleNameMap[tpl.targetRole] || null,
    assigneeRole: tpl.targetRole as string,
    stage: toStatus as string,        // ← tasks are tagged with their stage
    status: 'pendente',
    autoGenerated: true,
    createdByUserId: userId,
  }));
  await this.prisma.warrantyTask.createMany({ data: taskData });
  // ... then writes one WORKFLOW_TASKS history event.
}
```

Key facts the fix relies on (already true in the schema/code):

- Every auto-generated task is stamped with `stage = toStatus` and
  `autoGenerated = true` (`WarrantyTask` model in `backend/prisma/schema.prisma`
  has both `stage String?` and `autoGenerated Boolean @default(false)`).
- `generateAutoTasks` is called (best-effort, wrapped in try/catch) from three
  places — `updateStatus`, `approveWarranty`, `rejectWarranty`. You do **not**
  need to touch those call sites.

So "have this claim's tasks for this stage already been generated?" is answerable
with a single count query on `warranty_task` where `claimId`, `stage = toStatus`,
and `autoGenerated = true`.

### Step 1: Make generation idempotent per stage

In `generateAutoTasks`, **replace** the narrow loop-only guard with a general
"already generated for this stage" guard. Change this:

```ts

  if (fromStatus === 'AGUARDANDO_CLIENTE' && toStatus === 'EM_ANALISE') {
    return;
  }

  const templates = await this.prisma.warrantyTaskTemplate.findMany({
```

to this:

```ts
  // Idempotência por etapa: se este claim já teve tarefas automáticas geradas
  // para este status (toStatus), não gera de novo. Cobre tanto o retorno
  // AGUARDANDO_CLIENTE → EM_ANALISE quanto re-entradas via reversão/override
  // (ex.: APROVADO → revert → EM_ANALISE → APROVADO de novo).
  const alreadyGenerated = await this.prisma.warrantyTask.count({
    where: { claimId, stage: toStatus as string, autoGenerated: true },

    return;
  }

  const templates = await this.prisma.warrantyTaskTemplate.findMany({
```

Notes:
- The `fromStatus` parameter is now unused by the guard. Leave the parameter in
  the signature (the three call sites pass it) — an unused parameter is fine and
  keeping the signature avoids touching callers. Do not delete it.
- Do not change anything below the templates query.

### Step 2: Add a regression test

manual-mock style from plan 001 if absent). The test calls `generateAutoTasks`

simplest reliable test mocks Prisma and asserts that when

## Maintenance notes

- For the reviewer: the guard keys on `(claimId, stage, autoGenerated)`. If a
  future feature ever needs to *intentionally* regenerate a stage's tasks (e.g.
  a "reset workflow" action), it must first delete the existing auto-tasks for
  that stage, or this guard will silently skip generation.
- Existing duplicate tasks already in the database (created before this fix) are
  not cleaned up by this change — it only prevents new duplicates. If prod has
  visible duplicates, a one-off cleanup (delete the newer duplicate auto-tasks
  per claim+stage+title) can be run separately; out of scope here.
- Manual tasks (`autoGenerated = false`) are unaffected by the guard — only
  auto-generation is deduped.
